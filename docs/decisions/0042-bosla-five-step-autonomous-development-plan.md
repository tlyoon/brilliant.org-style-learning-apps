# Decision 0042 — Bosla five-step autonomous development plan

**Approved by the owner:** 15 November 2026. **Project:** Bosla / Brilliant-style learning apps. **Execution host:** Yoga 6 only. Applies to draft PR #223 and subsequent development work. This is an ongoing project plan, not a claim of background execution by ChatGPT or permission to bypass external denials.

## Binding development sequence

1. **Persistent Gemini diagnosis:** Implement a normal-path, key-safe, source-free transport/model/account preflight with bounded status classification, durable evidence, finite circuit stops, and separate error families (401/403, 404, 429, 5xx, timeout). Record provider status codes without raw provider bodies, keys, private generated text or model prompts. A metadata GET is NOT proof that generation is healthy.
2. **Autonomous Yoga 6 recovery:** Run an owner-controlled one-shot worker under a persistent Yoga 6 scheduler. A restart must re-read exact frozen hashes, role claims, provider circuit, and durable machine-local coordinator state before launching any request. One new activity per eligible tick. No retries of ambiguous requests, source-bearing probes, unbounded cycles, device hopping, automatic merge or publication. Install only under the intended Windows account with the owner-assigned Yoga 6 host guard, never modify the original Yoga 6 checkout.
3. **Assess Gemini Batch API:** Investigate availability for the configured model, project, and client; decide whether bulk noninteractive educational reviews benefit, including per-item hashes, durable batch IDs and reconciliation after interruption. Source-free feasibility and cost are distinct from live acceptance. Do not submit a batch solely to test whether an earlier ambiguous request succeeded.
4. **Advance independent application development:** Continue six-section learner workflow, multilingual behavior, prerequisite/diagnostic routing, visual/accessibility functionality, learner-state privacy and deterministic browser regression without requiring Gemini API connectivity. Respect frozen package identities and no-publication policy.
5. **End-to-end release verification:** Demonstrate normal Yoga 6 restart/schedule recovery, evidence-bound reviewer completion, 108/108 real activities, browser and accessibility checks, source-grounded scientific and language QA, complete source-free regression plus exact-head hosted CI. Publication requires genuine release evidence and separate authorization; synthetic checks do not fabricate reviews.

## Immediate sequence

Implement Steps 1 and 2 now, run a bounded genuine Yoga 6 recovery test against a **new independent activity only** after the real circuit allows it, then scope Steps 3 and 4 concurrently. A test that returns 503/504 is a truthful provider blocker; never mark it as recovered. Any repeating blocker must create a reusable normal-path fix, adversarial test and recurrence registry entry. Status, owner, evidence and unresolved dependencies belong in this document and PR #223, not just in conversational context.
